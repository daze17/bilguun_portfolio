## Танилцуулга

<img src="/work/wms/wms-logo-wide.png" alt="logo" style={{ width: '50%' }} />

Төв агуулах болон нэг буюу түүнээс олон жижиглэнгийн дэлгүүртэйгээр үйл ажиллагаа явуулдаг Монголын жижиг, дунд бизнес эрхлэгчдэд зориулан хөгжүүлсэн вэб суурьт бараа материалын удирдлагын систем. Энэхүү систем нь барааны үлдэгдлийн хяналт, шилжүүлгийн зөвшөөрөл, борлуулалтын тайлан зэргийг ролиор ялгаатай нэгдсэн интерфэйс дээр уялдуулснаар компанийн эзэд цаасан дэвтэр, тарсан Excel файл, чатын мессежид найдалгүйгээр барааныхаа тоон мэдээллийг үнэн зөв байлгах боломжтой болж байна.

## Шийдвэрлэх асуудал

Агуулах, дэлгүүрийг зэрэгцүүлэн ажиллуулдаг Монголын ЖДБ-үүд ихэвчлэн бараа материалаа гар аргаар хөтөлдөг. Барааны үлдэгдэл нь дэвтэр эсвэл Excel-д бичигддэг бөгөөд шилжүүлэг эсвэл борлуулалт хийгдсэн агшинд тоо нь зөрж эхэлдэг; шилжүүлгийн хүсэлт Messenger буюу утсаар дамждаг; сар эцэст тоо тохирохгүй болоход хэн, юу, хэзээ хийснийг нягтлах ул мөр огт үлддэггүй.

Системийн шийдвэрлэхээр зорьсон тодорхой асуудлууд:

- **Барааны зөрүү** — агуулахаас явуулсан гэж бүртгэгдсэн тоо болон дэлгүүрт хүлээж авсан гэж бүртгэгдсэн тоо хоорондын зөрчил
- **Хүний алдаа** — нэг шилжүүлгийг цаас, хүснэгт, чатад дахин дахин хуулан бичих явцад үүсэх алдаа
- **Хоцрогдсон мэдээлэл** — хэн нэгэн гар аргаар нэгтгэх хүртэл эзэд нь барааны бодит төлвийг хардаггүй
- **Аудитын ул мөргүй** — зөрүү гарахад хэн, хэзээ, хэний зөвшөөрлөөр юу хөдөлгөснийг сэргээн тогтоох боломжгүй

## Судалгаа

Бүс нутаг болон дэлхийн хэмжээнд өргөн хэрэглэгддэг бараа материалын системүүд болох Oracle WMS, Odoo, мөн дотооддоо хөгжүүлсэн Veritech-ийг харьцуулан судлахад нэг ч систем Монголын ЖДБ-д бүрэн тохирохгүй байгаа нь харагдсан. Олон улсын системүүд нь логистикийн тусгай багтай том байгууллагуудад чиглэсэн үнэ, цар хүрээтэй; харин дотоодын шийдлүүд нь зөвхөн агуулах эсвэл зөвхөн жижиглэнгийн талыг шийддэг бөгөөд хоёрын зааг буюу яг ЖДБ-үүдийн бараагаа алддаг газрыг орхигдуулсан хэвээр үлдээдэг. Энэхүү систем нь яг тэр цоорхойд төвлөрсөн — агуулах↔дэлгүүр хоорондын шилжүүлгийг хоёр тус тусдаа модуль гэж үзэхгүйгээр, нэгдүгээр зэрэглэлийн ажлын урсгал болгон зохион бүтээсэн.

## Системийн зохиомж

Систем нь гурван давхаргат вэб аппликейшний бүтэцтэй:

- **Танилцуулгын давхарга** — Next.js 15 (App Router) фронтэнд, серверт-рендертэй, мобайлд дасан зохицсон, монгол хэлний интерфэйстэй
- **Бизнес логикийн давхарга** — JWT, Passport.js-ээр хамгаалагдсан NestJS REST API; эндпойнт бүрийг рольд суурилсан хандалтын хяналт (RBAC) шүүдэг
- **Өгөгдлийн давхарга** — Drizzle ORM-оор дамжсан PostgreSQL 17; төлөв өөрчилдөг үйлдэл бүрийг бүртгэдэг аудитын хүснэгттэй

Систем RBAC ашиглан хэрэглэгчийн гурван рольтой бөгөөд тус бүр төгсгөлөөс төгсгөл хүртэл уялдсан:

- **Админ** — агуулах, дэлгүүр, хэрэглэгчдийг үүсгэдэг; бүгдийг харах эрхтэй
- **Агуулахын менежер** — тодорхой агуулахын барааг удирдаж, дэлгүүр рүү хийх шилжүүлгийг эхлүүлдэг
- **Дэлгүүрийн менежер** — шилжүүлгийг хүлээж авч, борлуулалтыг бүртгэн, өөрийн дэлгүүрийн барааны үлдэгдлийг хариуцдаг

Шилжүүлгийн ажлын урсгал нь зохиомжийн гол төв юм: шилжүүлэг гэдэг нь төлөвтэй обьект бөгөөд агуулахын менежер үүсгэж, дэлгүүрийн менежер хүлээн авахдаа баталгаажуулж, систем нь шилжилт бүрийг аудитын лог-д бичдэг — чатын мессежээр хийгддэг хүлээлгэн өгөлтийг цахим гарын үсгийн ул мөрөөр сольсон.

## Технологийн стек

- **Фронтэнд**: Next.js 15, React, TypeScript, Tailwind CSS
- **Бэкэнд**: NestJS (REST API), TypeScript, нэвтрэлтэд JWT + Passport.js
- **Өгөгдлийн сан**: PostgreSQL 17, Drizzle ORM-той
- **Бүтээх хэрэгсэл**: Turborepo монорепо, pnpm workspaces
- **Дэд бүтэц**: Локал хөгжүүлэлтэд Docker; контейнержсэн сервис хэлбэрээр байршуулах боломжтой

## Хэрэгжүүлэлт

NestJS бэкэнд нь долоон модульд хуваагдсан бөгөөд тус бүр өөрийн контроллер, сервис, Drizzle схемтэй:

- **Auth** — нэвтрэлт, JWT олголт, нууц үгийн хэшинг
- **Users** — рольоор хүрээлэгдсэн хэрэглэгчийн CRUD
- **Warehouses** — агуулахын үүсгэлт ба барааны төлөв
- **Stores** — дэлгүүрийн үүсгэлт ба барааны төлөв
- **Transfers** — агуулах↔дэлгүүр шилжүүлгийн төлөвт машин
- **Sales** — дэлгүүрийн талаас хийгддэг POS бүртгэл
- **Audit** — бусад зургаан модулийн төлөв өөрчилдөг үйлдэл бүрийг зөвхөн нэмэх горимоор хадгалдаг лог

Турборепо монорепо ашигласан тул бэкэнд, фронтэнд, хуваалцсан TypeScript типүүд нэг газар амьдарч, хамтдаа build хийгддэг:

```
warehouse-inventory/
├── apps/
│   ├── api/        # NestJS REST API
│   └── web/        # Next.js 15 app
├── packages/
│   ├── db/         # Drizzle schema + migrations
│   └── shared/     # Shared types and DTOs
└── turbo.json
```

## Үр дүн

Хүлээлгэн өгсөн систем нь агуулахаас дэлгүүр хүрэх бүхий л урсгалыг бүрэн хамарсан:

- Олон агуулах, олон дэлгүүрийн барааны үлдэгдлийг ганц dashboard дээр нэгтгэн харах
- Чат, цаасан хүлээлгэн өгөлтийг орлох цахим шилжүүлгийн зөвшөөрөл
- Төлөв өөрчилдөг үйлдэл бүрд автоматаар хийгддэг аудитын бүртгэл — хэрэглэгч, огноо буюу обьектоор хайлт хийх боломжтой
- Нэг компонентын номын санг хуваалцсан, гурван рольд тус тус тохирсон UI — админ, агуулах, дэлгүүр
- Мобайлд дасан зохицсон загвар (нэвтрэлт, sidebar, хүснэгт) — ингэснээр дэлгүүрийн менежерүүд утсаараа ашиглах боломжтой
- Эхнээс эцэс хүртэл монгол хэл дээрх интерфэйс

## Дүгнэлт

Энэхүү төсөл нь тодорхой зах зээлд чиглэсэн програм хангамж зохион бүтээх сайн жишээ болсон — тохиргооны уян хатан байдлаас илүүтэй аудитын ул мөр шаардлагатай Монголын жижиг бизнесүүдэд зориулсан шийдэл юм. Дараагийн алхам бол нэг түрээслэгчтэй (single-tenant) байршуулалтаас олон түрээслэгчтэй (multi-tenant) SaaS руу шилжих, мөн аудитын модулийг бүрэн хэмжээний тайлангийн давхарга болгон өргөтгөх явдал юм.
